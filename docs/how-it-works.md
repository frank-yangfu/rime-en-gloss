# 设计与性能取舍

这份文档记录「为什么不那么做」——每一条都是实际踩出来的坑，改动插件前请先读一遍。

## 1. 过滤器运行在宿主的输入线程里

Rime 的 `lua_filter` 是被同步调用的：你在微信里按下 `w`，微信的 UI 线程就会进入
`filter.func()`。这个函数返回之前，微信**整个界面都是冻结的**。

所以插件里被明确禁止的东西：

| 禁止 | 原因（实测现象） |
|---|---|
| HTTP 请求 / `simplehttp` | 每次按键都要等网络，输入直接卡死；另外 Windows 上的 `simplehttp.dll` 是 32 位，与 64 位 `rime.dll` 不匹配，调用直接报错 |
| `os.execute` / `io.popen` | 启动子进程会阻塞输入线程几百毫秒，且会闪黑窗 |
| 每次按键加载大 Lua 字典 | 曾有 3.5 MB 的 `en_dict.lua`，首次 `require` 冻结宿主 **1–2 秒**（微信、WorkBuddy 都复现过） |
| 遍历全部候选 | 拼音造句模式下候选可能几百个，强制生成全部候选会卡死宿主 |

## 2. 词表读取策略

`cache.txt` 有约 10 万行 / 2.4 MB，读取策略是三条约束下的折中：

- **只在缓存未命中时读盘**：命中率超过 99% 之后，正常打字完全不碰磁盘（同时避免杀软反复扫描导致的阻塞）。
- **每次按键最多解析 4 万行**（实测约 0.1 秒）：连打 3 个字整张表就全在内存里了，而任何单次按键的开销都可忽略。
- **每秒最多读一次**：避免按住键不放时反复 seek。

读取是**按偏移量增量解析**的：文件被重建（长度变小）时才整个重来。另外有一个
`fresh.txt`（几十 KB，存最近翻译的几百条），保证刚查过的词下一个按键就能命中，
不用等增量读取走到文件末尾。

## 3. 候选对象的构造方式

librime-lua 暴露的候选对象**没有 `end` 属性**（实测 dump：`type=table start=0 end=nil`）。
之前的写法 `Candidate(cand.type, cand.start, cand.end, ...)` 每次都抛错，被 `pcall`
吞掉后回退成原候选，于是「英文永远不显示」且日志里刷满 `with_comment failed`。

现在固定用 `Candidate("table", 0, #code, cand["text"], comment)` 构造：不读候选属性，
`comment` 槽拼成 `编码, 英文`。单字候选本身没有 comment，就用用户当前输入的编码兜底，
保证每一行格式一致。

## 4. 只挂 filter，不挂 processor

`lua_processor` 会参与**按键事件处理**。曾经挂过一个 processor，结果它一报错就把按键
处理链打断，表现为「完全打不出汉字」。翻译只需要看候选列表，所以只挂 filter。

## 5. Windows 下 WeaselServer 的生命周期

`WeaselServer.exe` 由 Windows IME 框架按需启停：没有活动输入框时它可能不在进程列表里，
这不代表故障。改动 lua 后**不需要重新部署**，重启 `WeaselServer.exe` 就会重新加载；
但改动 schema（`.yaml`）必须部署，而且要**先杀掉 WeaselServer**——部署器会等它释放锁，
否则会长时间卡住。

另一个坑：Rime 的增量部署可能判定「无需重建」。改了 schema 却没生效时，删掉
`build/` 目录强制全量重建最省事。

## 6. 沙箱/代理环境

如果在带 `http_proxy` 环境变量的 shell 里启动 helper 服务，进程会继承该代理，
所有外网请求都会失败（表现为 `10061 connection refused`）。启动脚本里应先清空
`http_proxy` / `https_proxy`。本项目默认不访问网络，所以只有可选的 helper 会受影响。
